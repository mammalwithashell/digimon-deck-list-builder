## Context

Local desktop bot games currently call the Rust engine with `Some(42)`, so every app launch produces the same deck order. The browser `/games` API already accepts an optional seed and randomizes with `secrets.randbits(64)` when omitted, while room matches generate a seed internally to implement first-player selection but do not expose or accept that seed as user-controlled debug metadata.

The frontend needs one consistent concept: a game has an effective seed, represented to users as a copyable decimal string. That seed must be available after creation and during terminal result review so a useful failure can be repeated.

## Goals / Non-Goals

**Goals:**

- Randomize bot and room game deck order by default.
- Allow a user-entered seed to reproduce bot and room match setup.
- Surface the effective seed in-game and on the result overlay.
- Make room explicit-seed mode reproduce the whole setup, including first player.
- Return from win/loss results to the launcher route after the user leaves the result screen.

**Non-Goals:**

- Changing engine action IDs, observation tensors, legality masks, or card-effect semantics.
- Adding recording/replay import from a seed plus action log.
- Guaranteeing compatibility for seeds generated by older builds that used different engine shuffling internals.
- Adding hidden auto-decisions to resolve first-player selection outside the existing seed/game initialization path.

## Decisions

### Represent UI-facing seeds as decimal strings

Frontend-visible APIs SHALL send and store seeds as decimal strings, even though the engine consumes `u64` internally.

Rationale: JavaScript cannot precisely represent every `u64` as a number. A decimal string keeps random 64-bit seeds copyable, pasteable, and lossless across Tauri, browser JSON, room state, and bug reports.

Alternatives considered:

- JavaScript `number`: simpler, but corrupts seeds above `Number.MAX_SAFE_INTEGER`.
- Hex strings: compact and exact, but less friendly for users copying from the UI.

### One effective seed per game

Every game creation path SHALL choose exactly one effective seed before engine initialization and return that seed with the created game metadata.

Rationale: this avoids drift where the engine uses one seed, the UI displays another, or room first-player logic mutates a user-provided seed after the fact.

Alternatives considered:

- Generate seed only in frontend: makes server-created room games and reloads harder to verify.
- Display the requested seed only: fails when the request is blank and the backend chooses the actual random seed.

### Explicit room seed controls first player

For room matches, an explicit seed SHALL be authoritative for the full initial setup, including first player. While explicit seed mode is active, the first-player selector is read-only or disabled in the UI and ignored by the server start path.

Rationale: repeatability is only useful if a pasted seed reproduces all seed-derived initial conditions. The existing first-player selector can remain for default/random mode by generating a seed compatible with the chosen player.

Alternatives considered:

- Preserve independent first-player override after seed entry: user-visible seed would not fully replay the game.
- Add a second "first player override" debug value: more flexible, but creates two values to copy and increases room lobby complexity.

### Do not auto-redirect at terminal result

The game SHALL keep showing the terminal result overlay until the player chooses the return action. That action resets transient game state and navigates to `/`, which resolves to the desktop launcher in desktop builds.

Rationale: the player asked to grab the seed while in game, and immediate redirect would remove the best moment to copy it after a bug or loss.

Alternatives considered:

- Automatic redirect on win/loss: simpler, but prevents result/seed review.
- Route directly to a legacy home screen: preserves old behavior but misses the launcher requirement.

## Risks / Trade-offs

- Seed parsing may diverge between Rust, Python, and TypeScript -> centralize validation rules in API helpers and test max/min/range cases.
- Room UI can become confusing when first-player is disabled by explicit seed -> label the disabled control with seed-derived behavior and re-enable it when the seed is cleared.
- Existing deterministic tests may rely on implicit `42` -> update tests to pass an explicit seed and add a random-default regression test.
- Full replay still requires the same engine version and card data -> copy text should identify the value as a shuffle/game seed, not a complete replay file.

## Migration Plan

1. Add seed fields in DTOs and frontend types as optional/backward-compatible metadata.
2. Replace the desktop hardcoded seed with generated random default while updating tests to pass explicit seeds where determinism is required.
3. Add room seed state and start semantics behind the existing room-match start flow.
4. Add frontend controls/display and result navigation.
5. Rollback by removing the new UI controls while leaving seed response metadata harmlessly ignored by older clients.
