# Rust engine gap-closure plan — Medusamon

## Goal

Close the 31 blocking and 1 partial engine gaps below so that **Medusamon** (meta_share 4.99%, 94 decklists, 53 unique cards) can be fully implemented in `digimon-engine/` without stubs, approximations, or auto-selections (per CLAUDE.md §17–18).

The archetype is red/LIBERATOR-centric and pivots on three tentpole mechanics the current Rust engine does not yet expose:

- An **"opponent's security stack was removed from"** recurring observer that gates the inherit effects on 15+ cards.
- **Petrification Tokens** — full token infrastructure with baked-in abilities.
- **Face-printed keyword parsing** — Progress, Raid, Piercing, Blocker, Armor Purge and friends on 17+ cards.

## Gaps to close (ordered by blast radius)

Counts below reflect Medusamon archetype only — most of these primitives unblock far more cards across the full pool.

### Tier 1 — unblocks the majority of the archetype

1. **Global `OnOpponentSecurityRemoved` observer timing** (🔴, blocks 15 cards) — the archetype's core engine. BT21-008, BT21-017, BT21-025, BT24-018, BT24-016, BT21-001, BT24-008, BT18-087, BT21-093, BT21-029, EX11-008, P-189, BT24-012, BT24-001, BT14-001 all gate their main recurring payoff on this trigger. See `docs/RUST_ENGINE_GAPS.md` "Global `OnOpponentSecurityRemoved` observer timing".
2. **Native printed keyword parsing** (🔴, affects 17+ cards) — Rush/Raid/Piercing/Blocker/Reboot/Jamming/Blitz/Vortex/Alliance/Security A.±N all live in `effect_text: String` today. See "Native printed keyword parsing".
3. **Option card play flow + `<Delay>` keyword** (🔴, blocks 10 cards) — every Option card in the archetype (P-103, LM-027, BT24-089, BT8-097, P-035, BT21-093, EX7-074, P-151, P-206, BT1-090) is wedged by §9's "Option cards have no play flow yet" gap. See "Option card play flow" and "`<Delay>` keyword".
4. **Play-from-hand / trash without paying cost + effect-initiated digivolve with cost reduction** (🔴, blocks 11+ cards) — BT21-017, BT21-025, BT24-016, BT24-082, BT24-089, LM-027, P-189, P-151, EX7-074, P-206 + the digivolve-offer siblings (BT21-001, BT21-093, BT23-005, BT21-013, P-103). See "Play-from-hand / trash without paying cost" and "Effect-initiated digivolve".
5. **Reveal top N deck + `add_to_hand` + ordered deck-bottom placement** (🔴, blocks ~10 cards) — BT21-008, P-103, P-035, EX7-074, BT16-082, P-151, P-206 plus sibling search effects. Ordered-selection primitive feeds this and several other gaps.
6. **`<Progress>` keyword + `ImmunityToOpponentEffects` modifier** (🔴, affects 6 cards) — the archetype's signature survivability. Distinct from native-keyword parsing because the enum variant + modifier type must be added first.

## Ask

Produce a phased implementation plan (per `superpowers:writing-plans`) that:

1. **Groups gaps by subsystem**, with clear inter-phase dependencies:
   - **Phase A — Observer plumbing:** fire the timings already declared in `enums.rs` (`OnEnterFieldAnyone`, `OnDigivolve`, `OnSuspend`, `OnLeaveField`, `EndOfAttack`, `WhenAttacking`, `OnSecurityCheck`, `OnAnyDeletion`). This phase alone unblocks ~20 cards, mostly via gap #1 (opponent-security-removed observer). No new data types — just dispatch sites + builder constructors + a handful of tests.
   - **Phase B — Native keyword parsing** (gap #2): one architectural decision — parse `effect_text` at registry build, or add `CardData::keywords: Vec<Keyword>` + ingest. Unblocks ~17 cards' face-keyword behavior in one shot.
   - **Phase C — Zone-manipulation helpers** (gaps #4, #5, #9, #10): `play_from_hand_free`, `play_from_trash_free`, `return_to_hand`, `return_to_deck`, `reveal_top`, `add_to_hand`, security-stack ops. Mostly additive to `EffectContext`; each needs a behavioral test.
   - **Phase D — Selection primitives** (gap #12 + #24 + #25): opponent-as-selector, cross-side, union-zone, ordered permutation, multi-select-with-sum. These share the `install_field_selection` machinery.
   - **Phase E — Option card play flow + `<Delay>`** (gap #3): architectural; needs its own spec under `docs/superpowers/specs/` before implementation. Depends on Phase C (most Option [Main] bodies need the zone helpers).
   - **Phase F — Token infrastructure + `WhenWouldBeDeleted` replacement framework** (gaps #7, #8, #13): `CardKind::Token`, `TokenRegistry`, Petrification Token data, replacement-effect plumbing. `<Armor Purge>` is a downstream consumer.
   - **Phase G — `<Progress>` keyword + `ImmunityToOpponentEffects` modifier** (gap #6): threads the immunity check through every opponent-targeting mutation site.
   - **Phase H — Raid target-switch interrupt + `OnAttackTargetChange`** (gap #11 + §22's target-switch observer): combat state-machine extension (`RaidOpen`) + event emission.
   - **Phase I — Cost reduction + dynamic DP infrastructure** (gaps #17, #18): closure-valued `cost_reduction_fn` + `dp_modifier_fn` + selection-gated BeforePayCost cost hook.
   - **Phase J — Player-scoped modifier registry + new ModifierType variants** (gaps #19, #20): `ModifierRegistry` extension + specific `ModifierType` additions.
   - **Phase K — Tier-3/4 keyword infrastructure** (gaps #14, #15, #16, #26, #27): De-Digivolve primitive, `<Training>`, Ace Overflow, alt-digivolve, Plug-In / Link (likely its own spec).
   - **Phase L — Misc helpers** (gaps #21, #22, #23, #28, #29, #30, #31): phase-granular timings, event-scoped observers, scheduled EOT queue, effect re-firing, force-follow-up-attack, trait-filter sugar.

2. **Orders phases by dependency and blast radius within each dependency tier:**
   - Observer plumbing (A) and native keyword parsing (B) share no dependencies and deliver the highest card coverage per unit of work. Run in parallel if practical.
   - Zone-manipulation helpers (C) are prerequisites for both Option flow (E) and digivolve/security effects across the archetype. Land early.
   - Selection primitives (D) enable ~8 currently-blocked cards and are prerequisites for Option play flow (E) and DNA-digivolve from effects (part of K).
   - Option flow (E) gates 10 cards; do NOT attempt before C is green.
   - Tokens + replacement framework (F) are co-dependent — `<Armor Purge>` lives in the replacement layer, Petrification Token's deletion trigger uses the security-stack ops from C.
   - Progress (G), Raid (H), and the Tier-3 modifier work (I, J) are largely independent and can run in parallel after the observer + keyword foundation.

3. **For each phase, lists:**
   - API surface to add (exact function signatures, enum variants, builder methods, `ModifierType` additions).
   - Tests to write FIRST (TDD per CLAUDE.md §18) — name the `digimon-engine/tests/*.rs` file and test case per primitive. Most new primitives need both a minimal "happy path" test and a selection-timing test that proves the player choice reaches `pending_selection`.
   - Affected Rust files.
   - Parity implications — which `docs/RUST_PYTHON_PARITY.md` entries does this resolve? Which does it create?
   - Explicit **out-of-scope** list to prevent scope creep (e.g., Phase A shouldn't touch `ModifierRegistry`).

4. **Flags architectural gaps that warrant their own spec under `docs/superpowers/specs/`** before implementation, not buried inside a phase:
   - Option card play flow + `<Delay>` (gap #3) — interacts with mask, effect queue, permanent identity, and placed-vs-resolved semantics.
   - `WhenWouldBeDeleted` / leave-field replacement framework (gap #8) — a general replacement-effect layer that many future cards will consume.
   - Plug-In / Link mechanic (gap #27) — entirely new zone-transition semantics.
   - Native keyword parsing (gap #2) — one-time but architectural; picks between `CardData.keywords` field + ingest pipeline vs. text-parse-at-registry-build. Decide the approach before committing engineering.

5. **Does NOT attempt to close every gap in one phase.** Prefer 3–6 phases with clear stop points. A reasonable first landing zone is Phases A + B + C + G, which collectively unblock ~60% of the archetype and require no architectural specs. Phase E (Option flow) should be a separate milestone.

6. **Preserves the no-approximations contract (CLAUDE.md §17–18).** Every phase's acceptance criterion must explicitly re-verify that player choices surface through `pending_selection` — no auto-selections, no silent drops, no cost-pay shortcuts. The TDD tests should include "player PASS / decline" branches for every optional effect.

7. **Does not author card scripts.** This plan is engine-only. Once the primitives land, `/batch-implement-cards-rust Medusamon` is the consuming skill.
